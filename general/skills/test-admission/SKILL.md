# 测试准入规范（Test Admission）

## 0. 核心立场

测试代码也是代码，同样要维护。**只有当一个测试在整个生命周期里的收益大于成本时，才允许加入。**

你的目标是**用最少的测试换来对正确性最大的信心**，不是测试数量最多，也不是覆盖率最高。

好测试同时满足四个条件，任何一项接近零，这个测试就基本没有价值：

1. **防回归**：代码出错时，测试能把它查出来。
2. **抗重构**：只改实现、不改行为时，测试不会失败。
3. **反馈快**：运行快，可以经常跑。
4. **易维护**：容易读懂，搭建环境简单。

---

## 1. 何时使用本规范

- 用户要求“写测试”“补测试”“提高覆盖率”。
- 你实现或修改了功能代码，准备附带测试。
- 修复 bug。
- 审查、重构或清理现有测试。

**默认行为：** 不要因为“顺手”就为每个函数生成测试。没有用户明确要求时，只为第 3 节“值得测试”中的内容补测试。

---

## 2. 准入原则（必须遵守）

### R1 测行为，不测实现
- 只通过**公开接口**断言**外部可观察的结果**：返回值、状态变化、对外副作用。
- 禁止断言私有方法、内部调用顺序、中间数据结构。
- 判断方法：换一种实现，只要行为不变，测试必须仍然通过。

### R2 按风险投入
测试力度和“出错概率 × 出错代价”成正比：

| | 依赖少 | 依赖多 |
|---|---|---|
| 逻辑复杂或业务关键 | 重点做单元测试 | 先建议重构拆分，再测 |
| 逻辑简单 | 不测 | 少量集成测试 |

### R3 不测别人负责的东西
- 不测语言、标准库、框架、第三方库本身是否正确。
- 只测**我们怎么使用它们**（配置、集成方式），而且放在集成测试层面。

### R4 平凡代码不单独测
getter/setter、常量、纯数据类、透传方法、自动生成的代码（protobuf、ORM 声明等）不写专门的测试。

### R5 不得抄写实现
预期值必须来自**规格或手算的具体样例**，不能复制被测逻辑来算。

```python
# ❌ 同义反复
assert calc_price(q, p) == q * p * (1 - DISCOUNT)
# ✅ 具体样例
assert calc_price(quantity=2, unit=50) == 90
```

### R6 测试必须有可能失败
- 禁止没有断言、断言过弱（`assert result`、`is not None`），或者断言 mock 自己返回值的测试。
- 自查：在心里把被测代码改坏（比如改掉某个比较运算符、删掉某个分支），测试是否会失败？不会就不准加。

### R7 mock 要克制
- 只 mock **进程外、不受我们控制的依赖**：第三方 API、消息总线、邮件或短信服务。
- 进程内的协作对象用真实实现。自己掌控的数据库优先用真实实例或轻量替身。
- 禁止“调用 mock，再断言 mock 被调用”这种循环验证，除非这次调用本身就是对外契约（例如必须发出某条消息）。

### R8 选最低的有效层级，避免重复
- 遵循测试金字塔：单元测试多，集成测试适量，端到端测试少。
- 同一条规则**只在一个层级上详细验证**。更高层只验证组装是否正确。
- 加测试前先搜索现有测试，已有覆盖就不要重复。

### R9 稳定、可复现
- 测试之间相互独立，不依赖执行顺序、真实时间、随机数、网络或全局状态。
- 时钟、随机种子、外部输入通过注入控制。
- 发现时好时坏的测试，要修好或删掉，不允许保留。

### R10 用等价类和边界值选用例
- 每个等价类取一个代表值，重点放在边界：0、1、最大值、空集合、溢出、非法输入、时区或闰年。
- 同类输入可以用参数化合并写，但不要为了显得全面而堆用例。

### R11 修 bug 必须补回归测试
先写能复现缺陷的失败测试，再修复，确认它由红变绿。

### R12 覆盖率不是目标
不得为了提高覆盖率写只执行代码、不检查结果的测试。覆盖率只用来**发现遗漏**。

### R13 测试即文档
- 测试名说明一条业务规则：`test_expired_coupon_is_rejected`，不要写 `test_coupon_3`。
- 采用 Arrange / Act / Assert 结构，每个测试只验证一个行为。

### R14 测试也要清理
功能删除后，删掉对应测试。冗余的、过时的、锁死实现的测试应当主动提出删除或合并。

## 3. 准入判定

### ✅ 值得测试
- 核心业务规则：计价、计费、权限、校验、状态流转。
- 算法和数据转换：解析、序列化（往返一致性）、格式转换。
- 边界和异常路径：空值、极值、非法输入、超时、重试、部分失败。
- 系统边界上的契约：对外 API 的格式，与外部服务的交互协议。
- 与真实基础设施的集成点：SQL、事务、迁移脚本、配置加载。
- 历史上出过 bug 的位置。
- 并发、幂等性、安全相关的逻辑。
- 少量关键用户路径的端到端冒烟测试。

### ❌ 禁止添加
- getter/setter、常量、纯数据类、自动生成代码的测试。
- 验证语言、标准库、框架行为的测试。
- 抄写实现来计算预期值的测试。
- 断言私有方法、调用次数、调用顺序等实现细节的测试。
- 只验证“mock 返回了 mock 设定的值”的测试。
- 没有断言或断言过弱的测试。
- 在多个层级重复验证同一规则的测试。
- 同一等价类里的冗余用例。
- 为了覆盖率而写的空洞测试。
- 依赖时间、网络、执行顺序的不确定测试。
- 大块输出的快照测试，而且没人审查差异。

## 4. 准入检查清单（每个新测试都要逐条通过）

有任何一条答“否”，就**不得添加**这个测试：

1. 它验证的是一个有业务意义的**可观察行为**吗？
2. 被测代码**确实可能出错**吗（有分支、计算或集成风险）？
3. 这个行为由**我们自己的代码**负责吗？
4. 预期值是**独立得出**的吗？
5. 改坏被测代码时，它**会失败**吗？
6. 只重构、不改行为时，它**仍会通过**吗？
7. 这个行为**还没被覆盖**，而且放在了能证明它的**最低层级**吗？
8. 它是**确定性的**、运行够快吗？
9. 光看测试名，能看出它**保护的是哪条规则**吗？

---

## 5. 工作流程

1. **识别行为**：列出被测单元对外承诺的行为和业务规则，不要列函数清单。
2. **风险评估**：按 R2 分类，跳过平凡代码和别人负责的代码。
3. **查重**：搜索现有测试，确认没有已覆盖的内容。
4. **设计用例**：按 R10 列出等价类和边界，每类一个用例。
5. **选层级**：按 R8 决定写单元测试、集成测试还是端到端测试。
6. **编写**：遵守 R1、R5、R7、R9、R13。
7. **自检**：用第 4 节的清单逐条检查，不通过的删掉。
8. **报告**：按第 6 节的格式向用户说明。

---

## 6. 输出要求

完成测试相关任务后，必须附上简短的准入说明：

```text
新增测试：
- test_xxx —— 保护规则：<一句话>；层级：单元/集成/E2E；风险依据：<为什么值得测>
有意未测：
- <对象> —— 原因：<平凡代码 / 框架行为 / 已被 test_yyy 覆盖 / ...>
建议删除或合并（如有）：
- <测试名> —— 原因：<违反的原则编号>
```

如果用户要求的测试违反本规范（例如“给所有 getter 写测试”“覆盖率做到 100%”），先简要说明会带来的成本和推荐做法。用户坚持的话，按用户要求执行，并在报告里注明。

---

## 7. 一句话准则

**只测有风险、有价值、可观察的行为。平凡代码、别人的代码、实现细节，以及永远不会失败的断言，都不该测。**
